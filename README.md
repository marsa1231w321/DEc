# DEc — передача проекта команде

Краткий входной документ для разработчиков и тестировщиков. Прочитайте его перед изменениями, затем обязательно изучите [DEVELOPMENT_GUIDE.md](./DEVELOPMENT_GUIDE.md), [PLAN.md](./PLAN.md) и [DEVELOPMENT_PROGRESS.txt](./DEVELOPMENT_PROGRESS.txt). Руководство подробно объясняет, куда обращаться за изменением каждой подсистемы, и является динамическим: его нужно пересматривать и обновлять при каждом изменении проекта. План задаёт зависимости и порядок работ; журнал фиксирует уже выполненные изменения и проверки.

## Состояние проекта

DEc — настольный прототип редактора 3D-сцен и карт на Python, Tkinter, GLFW и ModernGL. Редактор, 3D-вид, тестирование, ресурсы и анимация пока находятся в одном приложении. Это не готовый движок для выпуска коммерческих игр и не комплект из самостоятельных редакторов.

В рабочем прототипе есть создание и сохранение сцен `.DE`, примитивы и импорт сеток, три ортографические сетки, настройки света, простые логические правила, анимационные дорожки и кривые, процедурный авто-риг, просмотр ресурсов и тест от первого лица. Для описания текущего UX и ограничений см. разделы ниже.

**Архитектурное состояние важно не перепутать с roadmap:**

- Формат карт сейчас записывается как ZIP-контейнер `.DE` с `scene.json`, геометрией `meshes/*.npz` и встроенными назначенными текстурами/аудио. Манифест содержит `format_version: 6` и совместимый ключ `version: 6`; версии 1–6 проходят через явный миграционный слой, сохраняющий исходный номер для legacy-правил загрузчика. В `tests/fixtures/projects/` лежат golden-архивы версий 1–5.
- В рабочей копии реализован scene graph: он хранит узлы, связи, локальные/мировые transform и метаданные; `Scene.objects` и `Scene.lights` — неизменяемые представления для совместимости. F0.1 пока `PARTIAL`: CI и ручная проверка графического редактора ещё не подтверждены.
- Событийная шина `Scene.events` публикует типизированные события узлов сцены; редактор также рассылает события выбора, назначения ресурсов и общих undoable-изменений. Автосохранение и валидация пока не переведены на подписки, поэтому F0.3 остаётся `PARTIAL`.
- Отмена/повтор — первый вариант на снимках всей сцены в памяти, не `Command` API. Это не соответствует полному критерию F0.2/P2.1.
- Автокопия — один файл восстановления, не история версий/retention. Проверка сцены — базовая, без классификации blocker/warning и перехода к проблемному полю.
- Добавлены GitHub Actions, headless-тесты, Ruff и Pyright. Локальные проверки настроены, но удалённый запуск Actions и обязательность проверки для PR не подтверждены.
- F0.1 и F0.5 остаются `PARTIAL`: см. актуальные критерии и очередь в [PLAN.md](./PLAN.md). Не называйте локальные проверки подтверждением зелёного CI.

Актуальные статусы задач и причины блокировок ведутся в [PLAN.md](./PLAN.md). Исторические изменения и ручные проверки — в [DEVELOPMENT_PROGRESS.txt](./DEVELOPMENT_PROGRESS.txt).

## Быстрый старт

### Windows

Требуются Python, совместимый с синтаксисом проекта (минимум Python 3.10; поддерживаемый диапазон пока не зафиксирован), видеодрайвер/OpenGL 3.3 и установленные зависимости. Скрипт запускает `.venv`, если она есть, иначе использует `python` из `PATH`:

```powershell
.\start_engine.bat
```

Для разработки в новой копии репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

Импорт одной модели при старте:

```powershell
.\.venv\Scripts\python.exe main.py --model path\to\model.glb
```

В файле `requirements.txt` указаны нижние границы зависимостей, но точные версии не закреплены. Lockfile, политика обновлений и проверка установки на чистой машине — задачи Фазы 0.

### Требования и платформенные оговорки

- Основное приложение создаёт OpenGL 3.3-контекст через GLFW.
- На Windows GLFW viewport встраивается в Tkinter-окно через Win32 API. Вне Windows viewport может открываться отдельным окном; общего host-window backend пока нет.
- Для воспроизведения многих аудиоформатов требуется установленный FFmpeg `ffplay` в `PATH`. WAV может использовать системное воспроизведение Windows.
- Для обычного импорта моделей дополнительные форматы зависят от установленного `trimesh` и его optional-зависимостей.
- `.venv` — локальное окружение машины разработки, не источник истины о поддерживаемых версиях и не часть поставки.

## Проверки разработки

Локальные проверки CI и ручные smoke-проверки:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m ruff check dec_engine tests
.\.venv\Scripts\python.exe -m ruff format --check tests
.\.venv\Scripts\python.exe -m pyright
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m compileall -q main.py dec_engine
.\.venv\Scripts\python.exe smoke_test.py
```

GitHub Actions workflow находится в `.github/workflows/ci.yml`: Windows runners, Python 3.10 и 3.15, Ruff, Pyright и pytest. Ruff lint применяет базовые ошибки синтаксиса/стиля к `dec_engine` и `tests`; Ruff format пока проверяет `tests`, поскольку прежний код приложения ещё не приведён к форматированию Ruff. Pyright проверяет scene/runtime-модули и тесты, но не весь UI/renderer. В `tests/` есть unittest-тесты; pytest запускает их без переписывания тестового API. Headless-тесты проверяют scene graph, сериализацию, логику, валидацию и столкновения без создания GLFW/OpenGL-контекста. `smoke_test.py` остаётся короткой проверкой импорта и демосцены. `debug_render_test.py` открывает GLFW/OpenGL окно и предназначен для ручной диагностики графики. Ранее выполненные узкие smoke-проверки истории, recovery, валидации и UI описаны в журнале прогресса; они не сохранены как регрессионные тесты.

F0.5 остаётся `PARTIAL`, пока workflow не выполнится на GitHub и репозиторий не настроит его как обязательную PR-проверку. Локальные тесты и compileall не доказывают, что удалённый CI зелёный. Инструменты разработчика перечислены в `requirements-dev.txt`, общая конфигурация — в `pyproject.toml`; политика полной фиксации версий остаётся задачей F0.8.

## Как начать работу над задачей

1. Прочитать [PLAN.md](./PLAN.md) целиком, особенно Pre, DoD и Risk затрагиваемой задачи.
2. Проверить, что Pre закрыты статусом и проверяемыми доказательствами. Если нет — не писать код для заблокированного шага; записать блокировку и вернуться к первым незакрытым предусловиям.
3. До BREAKING-изменения формата `.DE` или публичного API завершить/выполнить F0.4: версия формата, миграция, golden-данные и миграционный тест.
4. Перед реализацией определить проверку DoD. Изменения архитектуры/зависимостей сначала отразить в плане.
5. Проверить релевантные слои, сохранить чужие изменения, внести точечный патч, прогнать доступные targeted tests/build/smoke. Не выдавать ручную проверку за CI.
6. Обновить статусы/заметки в [PLAN.md](./PLAN.md) и фактическую запись в [DEVELOPMENT_PROGRESS.txt](./DEVELOPMENT_PROGRESS.txt). Не отмечать задачу завершённой без DoD.

## Архитектурная карта

Точка запуска: `main.py` → `dec_engine.app.main()` → `run_app()`. `run_app()` создаёт окно GLFW/OpenGL, демонстрационную сцену, рендерер и `EditorUI`, затем выполняет цикл кадров и игровой тест.

| Файл | Ответственность |
|---|---|
| `main.py` | Точка запуска приложения. |
| `dec_engine/app.py` | Инициализация GLFW/ModernGL, цикл приложения, камера, viewport, тестирование, дополнительный вывод. |
| `dec_engine/editor.py` | Tkinter UI, панели, сцена/свет/логика/анимация, импорт ассетов, история, автокопия и взаимодействие с проектом. Это крупный монолит; разделять в рамках отдельных согласованных задач. |
| `dec_engine/scene.py` | `Scene`, `MeshInstance`, `Light`; текущая простая модель данных без графа и ID. |
| `dec_engine/project.py` | ZIP сериализация карт `.DE`, чтение версий 1–6, распаковка встроенных текстур/аудио во временный кэш. |
| `dec_engine/validation.py` | Базовая проверка геометрии, преобразований, ресурсов, света и правил логики. |
| `dec_engine/loader.py` | Импорт геометрии через `trimesh`, нормалей, UV и некоторых текстур. |
| `dec_engine/asset_pack.py` | Категории ресурсов и создание/чтение ZIP-пакетов `.DE` с `pack.json`. |
| `dec_engine/renderer.py` | ModernGL/OpenGL рендеринг, текстуры, свет, тени и редакторские гизмо. |
| `dec_engine/camera.py` | Камера, view/projection матрицы и направления движения. |
| `dec_engine/playtest.py` | Управление от первого лица, мышь/фокус, упрощённые столкновения и игровой звук. |
| `dec_engine/logic.py` | Выполнение текущего набора событий и действий карты. |
| `dec_engine/animation.py` | Интерполяция и применение animation tracks, в том числе костей. |
| `dec_engine/timeline.py` | Совместимость и вспомогательные операции камеры/ключей. |
| `dec_engine/audio.py` | Проверка и воспроизведение WAV/FFmpeg аудио. |
| `dec_engine/input_state.py` | Проверка состояния клавиатуры, мыши и фокуса приложения. |

### Основные потоки данных

- Сцена в памяти принадлежит `EditorUI` и передаётся рендереру и игровому контроллеру.
- `project.save_project/load_project` сериализуют карту; абсолютные пути остаются для внешних ресурсов, а встроенные текстуры и аудио карты получают URI `archive://` и временную копию в кэше.
- Asset pack и карта используют `.DE`, но различаются содержимым: `pack.json` для набора ассетов, `scene.json` для карты.
- Логика и физика сейчас прототипные: логика исполняется в цикле редактора, столкновения — упрощённые AABB/ландшафт; полноценного физического ядра нет.
- Авто-риг DEc создаёт семь процедурных костей и веса вершин; он не загружает исходный skinning/скелетные анимации сторонней модели.

## Формат проекта и совместимость

Карта `.DE` — ZIP, manifest `scene.json` указывает `format: DEcProject`, `format_version: 6` и совместимый `version: 6`; массивы сеток хранятся в NPZ. `migrate_project_manifest(old)` последовательно переводит manifest версий 1–6 к текущей схеме, сохраняя исходную версию; переход 3→4 переносит старые глобальные параметры направленного света в список `lights`. Golden ZIP-карты версий 1–5 и миграционные тесты находятся в `tests/fixtures/projects/` и `tests/test_project_migrations.py`. Пакеты ассетов (`DEcAssetPack`, версия 1) этим мигратором не затрагиваются.

Пакет ассетов `.DE` — ZIP с `pack.json` (`format: DEcAssetPack`, `version: 1`) и файлами внутри `assets/`. Это отдельная схема от карт, хотя расширение одинаковое. Формат не шифруется и не является механизмом доступа.

Перед изменением схемы/manifest, правил ссылок или семантики ресурсов обновляйте `CURRENT_PROJECT_FORMAT_VERSION`, добавляйте последовательную миграцию и golden-тест. Переходы без известных изменений пока сохраняют payload; историческое преобразование глобального освещения выполняется в `migrate_project_manifest`, а `load_project` получает уже нормализованный manifest.

## Текущее поведение редактора

Шаблоны в основном окне: **DEc Studio** (все вкладки), **DEc Map** (сцена/сетка/свет/логика/ресурсы), **DEc Motion** (сцена/анимация/свет/ресурсы). Шаблоны скрывают вкладки, но не удаляют данные. Разделители панелей изменяют размеры; дополнительный монитор и график кривых можно отделить в окна.

- **Сцена:** ящик, модель из файла/папки/ZIP, ландшафт, NPC, точка появления, источник звука, logic trigger; свойства имени, положения, поворота, размеров, цвета, текстуры, аудио и поведения NPC.
- **2D-сетка:** проекции X/Z, X/Y и Z/Y; перемещение/масштабирование маркерами, snapping и кисть высоты ландшафта.
- **Свет:** directional/point, цвет, интенсивность, направление, shadow map. Ограничения рендера — см. далее.
- **Логика:** on-start, timer, key, player-near; действия set-position, add-rotation, set-color, set-scale и toggle-visibility.
- **Анимация:** дорожки камеры/объектов/света/костей, ключи по времени и linear/smooth/Catmull–Rom интерполяция.
- **Ресурсы:** фильтрация/поиск пакета, предпросмотр моделей/картинок/звука, назначение ресурсов.
- **Тест:** WASD, мышь, Space, Esc; простые столкновения и ограниченная логика.
- **Первые версии улучшений:** undo/redo по snapshots, один recovery-файл, базовая валидация сцены. Эти реализации требуют дальнейшей архитектурной работы и имеют статусы `partial` в [PLAN.md](./PLAN.md).

## Ограничения и известные пробелы

- Scene Graph и стабильные ID реализованы частично; нет event bus, command API или атомарных транзакций.
- История undo хранит полные сериализованные снимки; покрытие операций не полное, состояние undo не сериализуется.
- Recovery хранит одну последнюю копию; интервал фиксированный, нет retention-настроек и интерфейса dirty-state.
- Валидация не имеет классов ошибок, отчёта с переходом к свойству и полной проверки анимационных/MTL-ссылок.
- Есть headless-набор, Ruff, Pyright и GitHub Actions-конфигурация; удалённый CI ещё не подтверждён, GUI/renderer остаются за пределами автоматических проверок.
- Расчёт теней использует один направленный источник; точечные источники не создают тени, учитывается до четырёх point lights.
- Поддержка модели зависит от `trimesh`; сложные материалы/submesh/skin могут теряться. Полный импорт анимации/экспорт сборки не реализован.
- Физика, player controller и NPC упрощены; нет fixed timestep simulation, broadphase/narrowphase/solver, collision layers или navmesh.
- Платформенное встраивание viewport связано с Win32. События GLFW обрабатываются опросом состояния в цикле кадров, а resize Tk-панели объединяется с задержкой 16 мс; ручная проверка привязки окна Windows Snap остаётся необходимой.
